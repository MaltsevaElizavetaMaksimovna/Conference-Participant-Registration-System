# Автообновление сервера

Поддерживается Linux amd64 с systemd и Docker Compose v2. Служба проверяет GitHub каждые пять минут. Она скачивает стабильный релиз в отдельный каталог и устанавливает его в окно обслуживания. При изменении схемы БД, настроек подключения или томов требуется ручное обновление.

## Публикация

Создайте тег `vMAJOR.MINOR.PATCH` на коммите с успешным запуском `CI` при push в `main`. Запустите workflow **Server release** из `main` и укажите тег. Workflow соберёт образы и опубликует стабильный релиз после загрузки архива. При прерванной публикации проверьте черновик и его вложение перед повторным запуском. Уже опубликованный тег сохраняйте неизменным.

## Первая настройка на ВМ

1. Войдите через bastion из сети ТПУ. Проверьте архитектуру, версию Compose, свободное место и доступ к GitHub API и адресу скачивания вложения. На диске должны помещаться архив, распакованные образы и свежая копия БД и фото. Зафиксируйте текущую версию, список Compose-файлов и идентификаторы работающих образов. Сохраните текущие файлы установки и образы `72a07aa` до репетиции отката.
2. Проверьте ранее созданный бэкап восстановлением в отдельную базу и чтением фотографии. Служба дополнительно создаёт и проверяет свежий дамп и архив фото перед каждым переключением. Если активен backup mirror, включите соответствующий overlay в конфигурации и проверьте, что независимый носитель смонтирован.
3. Из проверенной копии этого каталога установите файлы. Команды выполняются администратором ВМ.

   ```sh
   install -d -m 0700 /etc/regsys /opt/regsys-updater /var/lib/regsys-update
   install -m 0600 release_bundle.py github_release.py compose_update.py update.py /opt/regsys-updater/
   install -m 0644 regsys-update.service regsys-update.timer /etc/systemd/system/
   install -m 0600 update.example.json /etc/regsys/update.json
   ```

4. В `update.json` задайте абсолютные пути к текущей установке и её `.env.prod`, фактический список overlay-файлов в порядке запуска и текущий `initial_version`. Для первой установки поверх поставки с SHA без номера релиза используйте `v0.0.0`. Если репозиторий приватный, администратор может задать `REGSYS_GITHUB_TOKEN` в `/etc/regsys/update-token.env` с режимом `0600`. Для публичного репозитория этот файл не требуется.
5. Оставьте `maintenance` равным `null` и проведите проверку. В таком режиме разовый запуск сервиса только подготовит релиз на диске. Таймер пока выключен.

   ```sh
   python3 -B /opt/regsys-updater/update.py --config /etc/regsys/update.json --check
   systemd-analyze verify /etc/systemd/system/regsys-update.service /etc/systemd/system/regsys-update.timer
   systemctl daemon-reload
   systemctl start regsys-update.service
   journalctl -u regsys-update.service -n 30 --no-pager
   ```

6. Испытайте первый переход и возврат предыдущей версии на отдельном Docker-стенде с восстановленной копией. На ВМ задайте фактическое окно, например `{"timezone":"Asia/Tomsk","start":"03:00","end":"04:00"}`. Служба начнёт переключение только внутри окна, а начатое обновление или восстановление доведёт до конца. При первом применении проверьте `/health` по публичному домену, вход в панель и доступность ранее сохранённых фото и QR.

   ```sh
   systemctl enable --now regsys-update.timer
   systemctl list-timers regsys-update.timer
   ```

При неуспешном запуске служба возвращает предыдущие контейнеры с их конфигурацией на тех же томах и пропускает проблемную версию. При прерывании она пытается вернуть предыдущие контейнеры в следующий запуск. Состояние хранится в `state.json` под `state_dir`. Перед ручным вмешательством остановите таймер и дождитесь завершения активного сервиса. Сохраняйте предыдущий комплект Compose и образы до проверки следующей версии. Бэкап и история приложенных релизов могут занимать место, поэтому перед очисткой сверьте активную поставку и доступность отката.
