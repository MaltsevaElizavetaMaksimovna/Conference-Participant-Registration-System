# Развёртывание по HTTPS

Production запускается отдельным `docker-compose.prod.yml`. Caddy завершает TLS, раздаёт сборку SPA и проксирует `/api` и `/health` в FastAPI. Только Caddy публикует порты 80 и 443. Dev-конфигурация остаётся в `docker-compose.yml`.

## Подготовка

- Укажите `RS_PUBLIC_HOST` как DNS-имя без схемы, пути и порта. Оно должно разрешаться в адрес шлюза у панели, терминалов, агента и телефонов, которые будут открывать QR. Если профиль доступен только в LAN, телефон должен быть в этой сети.
- Задайте `POSTGRES_PASSWORD` и `RS_SECRET_KEY` в окружении оператора. Для новой БД подойдёт случайный шестнадцатеричный пароль. Так он передаётся в PostgreSQL и корректно попадает в URI. Для существующей БД пароль должен соответствовать текущему пользователю. Если в пароле есть символы, требующие кодирования в URI, задайте его URL-кодированную копию в `POSTGRES_PASSWORD_URI`. Обновление переменной само по себе пароль в БД не меняет.
- Для LAN оставьте `RS_TLS_ISSUER=internal`. Для публичного DNS-имени задайте `RS_TLS_ISSUER=acme` и обеспечьте доступ к портам 80 и 443 для проверки домена.
- Если подсеть `172.30.240.0/28` пересекается с сетью площадки, задайте свободную `RS_PROXY_SUBNET` и адрес Caddy внутри неё через `RS_PROXY_IP`. API принимает forwarded-заголовки только от этого адреса. Схема рассчитана на прямой вход через Caddy.

## Запуск

```sh
docker compose -f docker-compose.prod.yml config --quiet
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d --wait db
docker compose -f docker-compose.prod.yml run --rm --no-deps api python -m app.cli migrate
docker compose -f docker-compose.prod.yml up -d
```

Запускайте миграцию после перехода БД в `healthy`. Для пустой БД перед первым входом выполните `python -m app.cli bootstrap` в сервисе `api`, передав `RS_BOOTSTRAP_ADMIN_LOGIN` и `RS_BOOTSTRAP_ADMIN_PASSWORD` из окружения оператора.

Тома проекта `regsys-prod` хранят PostgreSQL, фото и резервные копии каталога приложения, данные TLS и конфигурацию Caddy. При переносе существующего стенда заранее сделайте резервные копии PostgreSQL и фото. Восстановите их в production перед запуском API, сохранив относительные пути фото и доступ на запись для пользователя контейнера UID 1000. Обычный `docker compose down` сохраняет тома. При откате поднимите предыдущие контейнеры на тех же томах, предварительно сверив совместимость схемы БД.

## Резервное копирование

Сервис `backup` запускается после готовности API. Он использует `pg_dump` и `pg_restore` версии 16, создаёт первую пару файлов при запуске и ждёт 30 минут перед следующим циклом. Дамп и ZIP с фотографиями сохраняются в `/home/app/backups` на томе `appdata`. Хранятся последние 48 комплектов.

Для независимой копии смонтируйте отдельный носитель на сервере и укажите его каталог в `RS_BACKUP_MIRROR_HOST_DIR`. Дайте UID 1000 доступ на запись в этот каталог. Проверьте, что носитель подключён после перезагрузки и Compose видит именно его. Используйте оба Compose-файла и при следующих обновлениях сервиса.

```sh
docker compose -f docker-compose.prod.yml -f docker-compose.backup-mirror.yml up -d backup
docker compose -f docker-compose.prod.yml logs --tail 50 backup
docker compose -f docker-compose.prod.yml exec backup python -m scripts.backup list
```

Сверяйте свежесть пары файлов и читаемость ZIP со второго носителя. Команда `python -m scripts.backup verify --file /backup-mirror/<имя>.dump` внутри контейнера проверяет дамп восстановлением во временную БД. Для запуска `now` вручную сначала остановите плановый контейнер, чтобы два процесса не писали в один каталог одновременно. [Сценарий приёмки](acceptance.md)

## Доверие и проверка

Получите публичный корневой сертификат LAN после запуска Caddy:

```sh
docker compose -f docker-compose.prod.yml cp edge:/data/caddy/pki/authorities/local/root.crt regsys-root.crt
```

Администратор добавляет этот сертификат в доверенные корневые центры рабочих станций и телефонов. Для процесса агента с HTTPX укажите абсолютный путь PEM-файла через `SSL_CERT_FILE`. Сохраните том Caddy с данными CA, иначе после его потери клиентам понадобится новый корневой сертификат.

Проверьте редирект с HTTP на HTTPS, `Strict-Transport-Security`, вход панели с `Secure` и `HttpOnly` у cookie и отказ при запросе без CSRF. Проверьте `/`, `/login`, прямую загрузку `/admin/settings`, `/api/terminal/ping`, heartbeat агента и ожидание задания через `/api/agent/jobs/next`. Запрос терминала к `/api/events/stream` должен получить `401`. В сессии сотрудника поток должен сразу отдать `stats`, продолжать keep-alive после 60 секунд и доставить регистрацию за 5 секунд. Для `/p/<token>` Caddy отдаёт SPA, а профиль берётся из `/api/public/profile/<token>`.

Журналы HTTP-запросов Caddy и Uvicorn отключены, чтобы URL профиля и данные запросов в них не попадали. Для диагностики проверяйте статус контейнеров и прикладные события.

## Выделенный HTTPS-вход для киоска

Вход включается дополнительным Compose-файлом. Для каждого устройства создайте
отдельное DNS-имя, например `kiosk-a.example.test`, и зарегистрируйте отдельный
терминал в панели. Сотрудники, телефоны и агент печати продолжают использовать
`RS_PUBLIC_HOST`.

1. Выпустите для устройства отдельный сертификат с назначением Client Authentication.
   На шлюз передайте публичную цепочку доверенного клиентского CA и **один**
   публичный сертификат устройства. Закрытый ключ устройства остаётся на киоске.
   Caddy проверяет цепочку и совпадение с закреплённым сертификатом. Если два
   киоска используют один CA, сертификаты всё равно должны быть разными.
2. Создайте закрытый каталог вне репозитория и задайте его абсолютный путь
   в `RS_KIOSK_CONFIG_DIR`. Создайте в нём `sites/`, `trust/` и `secrets/`.
   Скопируйте [пример сайта](kiosk-site.caddy.example) в
   `sites/kiosk-a.caddy`, укажите имя устройства и пути внутри контейнера.
   Разместите публичные PEM в `trust/`, а актуальный токен именно этого терминала
   в `secrets/kiosk-a.token`. Запишите только значение токена без префикса,
   BOM или перевода строки. На Linux ограничьте каталог режимом `0700`,
   файл токена — `0600`, с владельцем, доступным процессу Caddy. Каталог
   монтируется только в Caddy и только для чтения. Не включайте отладочные
   журналы HTTP-прокси и не выводите содержимое файлов токенов.
3. Проверьте конфигурацию. После успешной проверки пересоздайте только шлюз.
   Во время пересоздания HTTPS-вход кратковременно недоступен.

```sh
docker compose -f docker-compose.prod.yml -f docker-compose.kiosk.yml config --quiet
docker compose -f docker-compose.prod.yml -f docker-compose.kiosk.yml run --rm --no-deps edge caddy validate --config /etc/caddy/Caddyfile
docker compose -f docker-compose.prod.yml -f docker-compose.kiosk.yml up -d --no-deps --force-recreate edge
```

Киоск обслуживает `/`, ресурсы `/assets/` и операции терминала с разрешёнными
методами. Для POST требуется Origin, совпадающий с HTTPS-адресом
этого киоска. Для запросов API браузер также должен отправить
`Sec-Fetch-Site: same-origin`. Даже ping обновляет время последней связи.
Прокси подставляет токен после проверки TLS. Настройте
[сертификат и политику Edge](../agent/kiosk/README.md#выбор-сертификата-устройства).

Для отзыва сначала отключите терминал в панели. Удалите его файл из `sites/`
и пересоздайте шлюз, чтобы закрыть открытые TLS-соединения. Для замены сертификата
установите новый ключ на устройстве, замените публичный PEM на шлюзе и
пересоздайте шлюз до повторного включения терминала. Для ротации токена выдайте
новый токен в панели и атомарно замените файл в `secrets/` в пределах одного
каталога. Caddy читает токен при запросе. Для полного отката запустите команду
`up -d --no-deps --force-recreate edge` только с `-f docker-compose.prod.yml`.

## Синтетическая проверка

Соберите клиент в `dist`, подготовьте Caddy 2.11.9 и OpenSSL, затем запустите
сценарий из корня репозитория Python из `backend/.venv` с dev-зависимостями.

```sh
python deploy/tests/kiosk_smoke.py --caddy /path/to/caddy --openssl /path/to/openssl --spa /path/to/dist --scratch /path/to/scratch
```

Сценарий использует локальные порты и временную БД. Временные сертификаты и
тестовые токены создаются в указанном scratch-каталоге за пределами репозитория.
На Windows укажите пути к `caddy.exe` и `openssl.exe`. Настройку Assigned Access
и выбор сертификата из профиля Windows проверяйте отдельно на целевом устройстве.
