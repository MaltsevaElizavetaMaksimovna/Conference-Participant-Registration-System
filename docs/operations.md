# Запуск и эксплуатация локального стенда

Инструкция для текущего Python/FastAPI backend, React/Vite frontend и PostgreSQL 16.
Предложения Java из ранней переписки к этой версии репозитория не применяются.
Это локальный демонстрационный стенд; публикация в Интернет и TLS сюда не входят.

## Первый запуск

Нужны Python 3.12+ и работающий Docker Engine с Compose v2+.
Из корня клонированного репозитория выполните одинаковые команды в PowerShell,
cmd или bash:

```text
python scripts/configure_env.py
docker compose up --build -d --wait
python scripts/smoke.py
```

Первый скрипт создаёт .env с отдельными случайными паролем PostgreSQL и ключом
подписи; в консоль они не выводятся. Повторный запуск сохраняет существующий
файл. Пароль URL-safe, чтобы его можно было использовать внутри RS_DATABASE_URL.
Если меняете пароль вручную, используйте URL-safe символы либо согласуйте
процентное кодирование с настройкой SQLAlchemy URL. Изменение .env не меняет
пароль пользователя уже созданного PostgreSQL: для существующей БД нужна
отдельная процедура смены пароля, не удаление volume.

Миграции выполняются одноразовым сервисом migrate после готовности db.
API запускается только после успешного завершения migrate, web — после
готовности API. Ошибки миграций видны в docker compose logs migrate.

Интерфейс: http://localhost:8080. Swagger API: http://localhost:8000/docs.
Порты по умолчанию доступны только с текущего компьютера. Для терминалов на
других ПК нужен отдельно согласованный сетевой адрес: HTTP_BIND,
RS_PUBLIC_BASE_URL, RS_CORS_ORIGINS и правила доступа. Адрес localhost на чужом
ноутбуке указывает на чужой ноутбук, а не на сервер регистрации.

Caddy обслуживает /, /login и другие SPA-маршруты, сохраняет префикс /api
и проксирует /health. Фото участника использует относительный API URL.

## Первый администратор

Команда backend bootstrap уже существует. Передайте логин и пароль через
переменные окружения текущей оболочки, затем выполните:

```text
docker compose run --rm -e RS_BOOTSTRAP_ADMIN_LOGIN -e RS_BOOTSTRAP_ADMIN_PASSWORD api python -m app.cli bootstrap
```

Не вписывайте пароль в командную строку, Git или карточки YouGile. После
команды очистите переменные текущей оболочки. Bootstrap идемпотентен и создаёт
первого администратора только при отсутствии сотрудников. Он не является
командой сброса пароля существующей учётной записи.

Для вымышленных демо-данных отдельно: `docker compose exec api python -m app.cli seed-demo`.
Команда не выполняется автоматически и запрещена backend при RS_ENV=prod.

## Хранение данных и обновление

Volume pgdata хранит БД, photos — фотографии, backups — резервные копии.
Пересоздание API не удаляет фотографии; снимок БД не заменяет архив фото.
Обычная остановка: `docker compose --profile ops down`, без параметра volumes.
Не используйте `down --volumes` на стенде с нужными данными.

После обновления кода сначала сделайте и проверьте резервную копию, затем
выполните `docker compose up --build -d --wait`. Миграции и совместимость
обратного отката должны быть согласованы с backend-разработчиками.

## Резервное копирование

Используется существующий backend/scripts/backup.py; новый движок не добавлялся.
В образ API включены клиентские утилиты PostgreSQL 16. Профиль ops запускает
создание копии сразу, затем каждые 30 минут, оставляя последние 48 наборов:

```text
docker compose --profile ops up -d backups
docker compose logs --tail 50 backups
docker compose --profile ops run --rm backups python scripts/backup.py list
```

Разовая копия и проверка последнего дампа:

```text
docker compose --profile ops run --rm backups python scripts/backup.py now
docker compose --profile ops run --rm backups python scripts/backup.py verify
```

Verify восстанавливает дамп во временную БД того же PostgreSQL, проверяет
таблицы и удаляет только свою временную БД. Она не перезаписывает рабочую БД.
Это проверка дампа; физическое восстановление фотографий выполняется отдельно.
Скрипт loop продолжает работу после ошибки, поэтому проверяйте его логи.
Ротация не защищает от потери всего компьютера: выгружайте копии на второй носитель.

Чтобы скопировать наборы из volume на хост, сначала запустите сервис backups,
создайте локальный каталог, затем получите ID контейнера через
`docker compose --profile ops ps -q backups` и выполните
`docker cp <ID>:/srv/.data/backups/. <локальный-каталог>`.
Копии содержат персональные данные и не должны попадать в Git и CI артефакты.

## Восстановление после аварии

1. Сохраните текущую БД и фотографии отдельно. Остановите регистрацию и агент печати.
2. Проверьте выбранный .dump командой verify с `--file /srv/.data/backups/<имя>.dump`.
3. Вместе с backend-разработчиком восстановите дамп **в отдельную БД** утилитой
   pg_restore версии 16; не направляйте экспериментальную команду в рабочую БД.
4. Распакуйте соответствующий архив `*-photos.zip` в отдельный каталог, проверьте
   пути и содержимое. Сопоставьте количество участников, регистраций и наличие фото.
5. Только после проверки согласуйте переключение БД и photo volume. После
   переключения прогоните smoke и проверьте карточку участника в браузере.

В этом изменении автоматическая перезапись рабочей БД намеренно не добавлена.

## Проверки и диагностика

Smoke выполняет только GET: /health (включая SELECT 1), /, /login и /api/auth/me
(ожидается JSON 401 без сессии). Он выявляет ошибочный SPA fallback на API.
Он не регистрирует участников, не отправляет печать и не проверяет весь браузерный UX.

```text
docker compose ps --all
docker compose logs --tail 100 migrate api web
python scripts/smoke.py
```

В CI проверяются backend, агент на Linux/Windows, сборка frontend и полный
контейнерный сценарий: миграции, smoke, создание/проверка копии и сохранение
фото при пересоздании API. CI использует одноразовую БД; её удаление после
задания не является инструкцией удаления данных на рабочем стенде.
